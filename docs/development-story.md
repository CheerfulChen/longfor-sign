# 从一条签到请求，到一套自己的服务

> 博客筹备页。正文尚未发布，这里先保留文章提纲和可核实的开发脉络。

这个项目的起点很小：希望每天替自己的账号完成签到，并收到结果。真正写下去后，问题逐渐从“怎么发一个请求”变成“怎样确认它做完了，以及下一次还能正确继续”。

## 准备讲述的过程

### 1. 第一条请求：先让一个账号跑通

从抓包里定位真正的签到 POST，而不是页面配置请求或 OPTIONS。分清登录 token、设备风控值和活动参数，得到第一条能与客户端记录对应的成功结果。

### 2. 从一个账号到多个账号

让每个账号的 token 与风控值保持配对，处理失败并推送结果。账号顺序、等待间隔和消息中的名称，都开始成为需要设计的行为。

### 3. 搬进云函数：时间也是资源

函数有超时，等待会计入执行用量。全天随机不能靠在一次调用里睡上一整天，于是改成半小时检查、到期执行、无任务即退出。

### 4. 给函数一本记事本

用 OBS 保存每日计划、执行状态和推送记录。经历了 IAM 对象权限与桶权限的区别，也查清了“记录不存在却返回 403”的 ListBucket 问题。

### 5. 成功回包，不一定等于成功签到

加入签到日历复核，区分接口报错但实际已签、回包正常但状态未变，以及请求后无法确认结果。异常中断时，不能用盲目重试替代状态判断。

### 6. 续期之后，账号还是原来的账号

研究 `token2key → key2token`，保存更新后的登录凭据。再把计划身份与会变化的 token 解耦，避免一次正常续期被当成更换账号。

### 7. 两个入口与人机验证

区分小程序和 APP 的活动，按账号验证资格和结果。把设备指纹、验证码凭据与登录会话分开讨论；保留实验结论的适用范围，不把一次成功写成永久保证。

### 8. 下一步：把运行过程放进面板

公共核心、SQLite、管理员登录、定时任务和 Docker 部署已实现。基础脚本、Actions 与两种云函数也已统一调用公共核心。博客将记录从停车需求、验证码研究到云函数和服务器面板的过程，正文链接待发布后补充。
